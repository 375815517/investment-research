# 输入数据结构基线 v1

日期：2026-10-30（Asia/Shanghai）。状态：已确定的设计基线；本次落实文档、目录骨架与人工研究 Skills，不代表采集、自动校验、索引或宿主安装已实现。该描述为封版时状态。后续已完成主证券确认及首版输入平台，当前实施状态见[验收记录](../verification/input-platform-v1.md)，目录合同保持不变。

补充：[来源观测与覆盖扩展](../decisions/002-source-observations-and-coverage.md)明确 provider-native 保存与查询隔离，以及有证据的交易/披露预期。

本文是输入目录、归属和版本规则的唯一基线；其他架构文档和 Skills 引用本文。输出层沿用现有组织，本次不重新设计。后续调整输入合同应记录决定及迁移方案，不通过修改示例悄悄改变规则。

## 1. 目标与边界

企业自身资料归企业，行业、市场、政策等共享信息独立保存，通过有证据、有时间的关系关联。人和 AI 从企业入口集中查阅；可读性通过名称、字段说明和导航实现，不混放原件、采集过程和业务事实。

Git 保存定义、原件和正式结构化输入。大型文件按需启用 Git LFS；数据库、全文及向量索引可从指定版本重建。正式证据不得只存在于本地缓存。当前未配置 LFS；完整恢复若使用 LFS 必须取得对应对象。

价格建立市场反应的时间轴；财务、经营、行业和政策是独立原始证据。官方愿景、指引和外部预测是来源声明，不是已实现事实；我们的评分、推断和预测属于输出。

## 2. 职责与正式目录

| 位置 | 职责 |
| --- | --- |
| research/sources | 来源身份、接入、覆盖、频率、延迟、许可和限制的定义 |
| research/datasets | 数据粒度、字段、业务键、单位、时间、质量和修订规则的定义 |
| data/inputs/source-files | 外部原件的唯一归档；包括 PDF、网页、接口响应 |
| data/inputs/collection-records | 每次获取的范围、时间、结果、原件引用、失败和缺口 |
| data/inputs 下的业务目录 | 企业、行业、市场、宏观、政策与事件的结构化输入 |
| 业务批次中的 batch.json | 实际文件、摘要、覆盖、解析版本与质量状态 |
| 企业 README 与派生索引 | 聚合阅读入口，链接权威记录，不维护另一套事实 |

```text
research/
├── sources/<source_id>/source.yaml
└── datasets/<dataset_id>/
    ├── dataset.yaml
    └── README.md

data/inputs/
├── README.md
├── source-files/<source_id>/<archive_year>/<document_id>/<content_revision>/
│   ├── original.<source_format>
│   ├── document.json
│   └── extracted/<extraction_version>/       # 可选
│       ├── text.md
│       └── extraction.json
├── collection-records/<source_id>/<year>/<collection_id>/
│   └── collection.json
├── companies/<company_id>/
│   ├── README.md
│   ├── profile/
│   ├── strategy/
│   ├── businesses/
│   ├── financials/
│   ├── operations/
│   ├── guidance/
│   └── relationships/
├── industries/<industry_id>/
│   ├── README.md
│   ├── classification/
│   ├── supply-demand/
│   └── products/
├── markets/
│   ├── securities/
│   ├── prices/
│   ├── calendars/
│   ├── corporate-actions/
│   ├── benchmarks/
│   ├── universes/
│   ├── expectations/
│   └── exchange-rates/
├── macro/<region_id>/<dataset_id>/
├── policies/<policy_id>/
└── events/<event_id>/
```

尖括号表示合同参数，不创建占位数据。当前只创建共享目录骨架；对象、来源和数据集在实际建档时创建。具体实体记录以 record_id/revision 分开保存；表格以期间和批次分区，不强制所有数据使用同样深度。正式记录及批次不可原地覆盖。

不设 subjects/：companies/<company_id> 是唯一企业业务入口。不设独立 listings/：当前每家公司先确认一只主要研究证券。原件不按被研究公司归属；source_id 表示获取渠道，例如 xiaomi-ir 表示小米投资者关系来源，hkex-disclosures 表示交易所披露来源，均只是候选命名，不代表已接通。

## 3. 原件、采集与业务记录

一份原件可支持多个数据集，一次采集可取得多份原件，多次采集可取得相同内容。业务记录通过 document_id、content_revision、SHA-256 和 locator（页码、表格、JSON 路径、行键）引用原件。路径是定位信息，不是业务身份。

来源原件按实际格式保留，不把 JSON 响应强改成 PDF。归档年份是存储分区，不代替公开年份或报告期。同 URL 内容变化新增版本；相同字节重复获取只新增采集回执。跨渠道相同原件可引用已存在的权威文件，同时保留各次获取渠道与原始发布者；字节去重不等于证明不同报道相互独立。

PDF/网页提取文本保存提取版本、页码与原件引用。原件、OCR、财务字段解析是不同版本链；修复单位识别错误只新增解析结果，不伪造来源更新。

collection.json 至少记录 collection_id、source_id、去敏请求参数、请求期间、开始结束时间、取得的原件引用、实际覆盖、未取得范围、状态和失败原因。无新增、部分成功、失败分别表达；不把 HTTP 200 或文件存在视为完整可用。

## 4. 企业、行业与共享信息的归属

| 小米相关内容 | 权威位置与身份 |
| --- | --- |
| 年报原件 | source-files，共享原件 |
| 收入、利润、分部表 | companies/<id>/financials，带报告期与原件定位 |
| 官方长期愿景 | strategy，标记来源声明及适用条件 |
| 年度交付目标 | guidance，带目标期间、定义和发布时间 |
| 实际交付量 | operations，区分订单、锁单、交付等口径 |
| 主证券行情 | markets/prices，不在公司目录复制 |
| 行业销量、产品资料 | industries，保留地区、渠道、样本与来源方法 |
| 汽车补贴 | policies，保存条款、资格、阶段和有效期 |
| 政策发布或实施 | events，引用政策与原件 |
| 补贴可能提高利润 | 研究输出，不登记为输入事实 |

企业身份、官方业务分部、品牌和产品范围分开；研究者分类不能冒充公司正式分部。集团合并与单体、不同币种、累计与单季、出货与零售等不可因字段同名而合并。未知数据不填零。

持股、供应、客户等关系注明主体、客体、关系类型、适用产品/地区、有效时间、公开时间、来源与核实状态。关系默认由主体归档，逆向关系查询生成。竞争事实可保存产品价格、区域和渠道；‘竞争强度高’等判断属于输出。

政策适用于多个企业时只存一份。官方资格名单可支持适用关系；AI 推测‘可能相关’留在研究产出，不能进入已确认关系。来源观点、第三方估计与正式统计分别标记。

## 5. 股票行情的位置与主证券

首次企业建档时由用户确认主证券。企业 profile 引用 primary_security_id，保存选择生效时间和确认依据；证券档案保存发行企业、代码、交易所、币种、时区、股份类别及代码有效期。公司与证券 ID 独立；主证券变更新增映射版本，不直接拼接价格序列。市场及必要行业基准不属于公司的额外上市证券，仍可接入。

小米路径示意（不表示已确认或取得数据）：

```text
data/inputs/markets/
├── securities/xiaomi-hk/<revision>/security.json
├── prices/xiaomi-hk/daily/<year>/<batch_id>/
│   ├── daily-prices.csv
│   └── batch.json
├── corporate-actions/xiaomi-hk/<batch_id>/
└── calendars/<venue>/<year>/<revision>/
```

日行情保存未复权 OHLC、成交量及其单位、适用时的成交额、交易日期、时段、币种、交易状态、来源和版本。供应商日线是汇总观测，不称为逐笔原件。原始响应仍在 source-files，采集回执在 collection-records，标准化行情引用响应记录。

分红、拆并股、发行、回购授权/执行/注销分别记录。复权价与收益计算绑定公司行动和算法版本，属于派生结果；供应商提供的复权序列注明其方法、锚点和版本，不覆盖未复权价。

小观察池按证券/年/批次保存；一个原始响应含多个证券时仍只归档一次。全市场扩展可采用市场/时间/批次分区，需要版本化迁移方案。不要每股每日固定复制原件、清单等多个文件。LFS 不解决百万小文件问题。

## 6. 数据集、来源和批次的最小合同

以下为字段要求，不是已实现的 schema 或配置实例。

| 合同 | 必须说明 |
| --- | --- |
| source.yaml | 稳定来源 ID、名称、提供方、入口、覆盖、频率、延迟、认证类型、归档许可与已知限制；不含凭据 |
| dataset.yaml | 数据集 ID、schema_version、一行代表什么、业务键、字段、单位、时区、来源选择、修订解析、分区及质量规则 |
| document.json | 资料 ID、内容版本、发布者/渠道、标题、类型、对象关联、公开时间及精度、原件摘要、前版引用 |
| batch.json | 批次 ID、数据集版本、文件路径和摘要、覆盖范围、行数、原件及采集引用、解析版本、登记时间、质量与修订关系 |
| 业务记录 | 对象、指标或事件身份、期间/生效时间、值和单位、来源定位、来源身份与修订引用 |

主键随数据集定义：日线按证券/时段/日期/来源/价格口径，财务按企业/合并范围/指标/期间/币种单位，行业统计还需地区、产品、渠道、统计方法。不同来源的冲突观测保留，来源选择有依据，不能静默平均。

配置定义在 research，实际批次清单随业务文件保存。静态的数据集 README 解释口径；实际覆盖和新鲜度从批次与采集记录派生，避免重复维护。

## 7. 时间与历史区间研究

至少区分业务期间/事件时间、来源公开时间及其精度、首次观察与实际采集时间、生效区间、解析登记时间。时间带时区；未知或仅有日期不伪造分钟。Git 提交时间不能代替这些时间。

| 研究模式 | 允许的信息 |
| --- | --- |
| retrospective_explanation：事后解释 | 可用后续披露，逐条标明当时尚不可知；不冒充前瞻成绩 |
| historical_reconstruction：历史时点模拟 | 只用截止点前已公开且可证实版本的资料，允许后来补采 |
| live_observed：当时实际信息复现 | 还要求截止点前系统已取得并可供使用的版本 |

可复现输入解析至少固定对象、数据集、期间、截止点、模式、来源和修订选择规则。今天取得的重述财报不能替代旧版；盘后公告不能直接作为当日收盘前已知信息。历史关系、行业成员及主证券映射同样按时点读取。

后续指标探索使用共享输入合同，指标定义放 research/metrics，不在每家公司复制公式。具体研究输入冻结与输出登记沿用既有运行记录设计，本次不扩展。

## 8. 人与 AI 的阅读和检索

公司 README 是自身资料与共享资料的引用导航，显示主证券、战略、财务、经营、相关行业/政策/事件及覆盖缺口。公司是研究入口，不拥有所有相关原件。行业和政策也可反向查询关联公司。

可读稳定 ID（如 xiaomi）用于定位，display_name 与别名用于展示；改名不改变身份。字段说明写明‘统计谁、什么、哪里、何时、用什么口径’。生成导航和索引应注明生成依据和版本，不作为历史事实的替代品。

AI 依次解析对象 → 读取数据集口径 → 检查范围和时点 → 定位记录 → 核实原件。向量相似度仅作检索线索。覆盖状态至少区分 available、stale、missing、blocked、not_applicable，附原因和最后检查时间；未找到不等于不存在。

## 9. 质量、发布与恢复

原件保留，业务批次通过质量检查才进入默认查询。检查文件摘要和解析类型、身份、业务键、OHLC、单位、日期、覆盖与来源差异；未完成收盘、停牌、休市、来源缺数分别标记。极端行情先调查，不自动删除。

本地暂存 → 校验 → 完整批次 → Git 发布。失败不覆盖最近有效数据；采集和批次状态分开。原件修订、解析修订、合同修订分别表达。并发任务有独立 ID 与幂等检查，不能因 Git 自动合并成功就认定业务无冲突。正式状态更新追加记录或版本，旧清单保留。

来源受限时记录网络、认证、付费、限流或许可问题及覆盖缺口；不绕过限制、不用模型记忆补原件。可恢复档案包含 Git 和必要 LFS 对象；索引删除后能够重建。机器可执行校验、自动发布和恢复工具仍待实现。

## 10. 小米落地验收与演进

第一阶段验证一家公司、一只经确认的主证券和必要基准，不预先接入全市场或高频数据。验证场景：

1. 一份年报支持财务、业务和指引，原件只有一份。
2. 一批多证券响应，各自行情可追溯同一原件。
3. 一项政策被小米和其他企业引用，资格事实与影响推断分开。
4. 同原件解析纠错不产生假来源修订，旧结果仍可定位。
5. 重复采集、部分失败、缺行情、来源冲突均有明确结果。
6. 历史区间查询排除不合格未来信息，保留当时关系和版本。
7. 移动分区或删除索引后，稳定 ID 与内容摘要仍能恢复准确引用。

结构变更以以上场景为依据。新增来源主要增加接入与字段映射；新增企业主要增加对象和记录；规模变化调整物理分区，不改写业务身份。输出设计不在本次封版范围。
