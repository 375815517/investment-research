# ADR 005：输入平台的校验成本与扩展边界

状态：已实施第一阶段准入校验缓存；后续扩展保留为方向。日期：2026-10-30。

## 当前决定

正式数据继续以 Git 中不可变原件、追加批次与追加修订为权威来源。索引和缓存是可重建加速设施，不能代替原件哈希、批次内容一致性、审核绑定或 STALE_PLAN 门禁。优化落在现有 repository/engine 层，不增加平行的数据入口，也不为小米或腾讯提供特例。

本机采用单写入协调。多个 Agent 可以并行检索、下载到临时位置、提取候选和审核；正式 import、ingest、metadata revision 必须经过公共服务及其锁。当前读取快照也持有同一把排他锁，实际实现是读写校验串行，而不是已经实现“并发多读”。不能用增加 worker 数解决当前准入吞吐问题。

## 已证实的瓶颈

2026-10-30 在本工作区执行只读诊断，结果保存在 `data/outputs/research-records/input-platform-scaling-review-20261030/profile.json`。

| 诊断 | 规模与调用 | 实测耗时 |
| --- | --- | --- |
| `read_snapshot` 中计算一次 `revision()` | 126 批；126 次 document 调用；仅构建一次文档索引 | 0.346 秒 |
| 无快照缓存，持写入锁计算一次 `revision()` | 127 次构建文档索引 | 11.937 秒 |
| 快照外读取一个文档 | 构建一次全库文档索引 | 0.037 秒 |

当时统计为 211 份文档、126 个批次；两次测量间其他 Agent 正式追加了一个批次，所以两次 revision 不同。此表不是相同固定数据集的严格加速比或 SLA；耗时也包括取得锁的等待，不能据此分解 CPU 与磁盘占比。可以确定的是重复全库索引构建次数，以及请求级缓存已经具备的能力。

代码链路：

1. `Repository.document()` 在没有 read_snapshot 时，每次都扫描并解析全部 `document.json`，之后读取目标原件并计算 SHA-256。
2. `Repository.batches()` 遍历所有可见批次，验证每份文件哈希、实际行与 manifest 一致，并对每批的来源文档调用 document。同一 PDF 支持多个批次时，会重复构建索引及读取相同 PDF。
3. `Repository.revision()` 调用 batches，再对批次清单计算内容指纹；其语义是已完成批次集合版本，不是整个 Git 工作树、研究定义或全部 metadata 修订的版本。
4. `_ingest_plan()` 的 `_admission()` 与 `revision()` 分别读取批次；`_ingest_apply()` 在锁内再次运行 `_admission()`、批次基线比较及文档读取。因此单批约 30 秒的现场观察与多次全库校验相符，但不能将这个端到端时间全部归因为 SHA 算法。

若 D 为文档数、B 为批次数，无请求缓存时索引解析成本近似随 B×D 增长；同一来源的原件读取也随引用批次数重复。首要问题是重复工作，而不是 JSON/CSV 目录命名或立即替换数据库。

## 第一阶段安全优化（已实施）

优先复用已存在的请求级已校验视图，粒度必须是一个一致的校验阶段。

- plan 阶段：在只读快照中完成候选准入检查和 base_revision 计算，退出只读上下文后写本地 plan。正式 apply 仍重新校验，不复用 plan 阶段缓存作为提交依据。
- apply 阶段：持有写入锁后，在同一次已校验读取作用域中完成审核、全库批次验证和基线计算，随后退出读取缓存作用域再写批次。需要明确表达“已经持有锁”的内部作用域，不可简单嵌套现有 `lock()` 与 `read_snapshot()`；独立文件描述符上的 flock 可能形成自阻塞。
- 缓存限定于当前操作/阶段；第一次读取每份原件仍实际校验 SHA。进入下一次顶层调用、取得新事务视图或发生写入后必须失效。缓存返回副本，防止调用者改动共享对象。
- 可将每阶段文档元数据索引、已校验文档与已校验批次分别缓存。不要只依据 mtime/size 判定原件未变化，不要用“相同 document_id”替代内容验证。

已新增 `Repository.verified_read_view()`：要求当前同步上下文已持有本仓库锁，不再获取第二把 flock；退出时清除视图，视图内禁止 repository 写入。ingest_plan 使用独立 read_snapshot；ingest_apply 持有原写锁，在 verified_read_view 中完成幂等检查、准入与基线比较，退出后才写批次。plan 的缓存不会传给 apply。

已补 `tests/test_ingest_verified_view.py`，验证未持锁拒绝、禁止视图写入、返回值污染隔离、每阶段仅一次索引及一次锁、同大小原件变化、已有来源变化、失败清理后恢复、计划过期及连续准入、批次修改后下一视图重新拒绝。与 core、metadata 测试合计 36 项通过。验收还应持续覆盖：原件/批次同大小篡改、计划生成后新增批次、审核改变、重复准入、部分写入恢复、跨请求缓存失效、嵌套锁不死锁、并发读写可见性，以及优化前后完全相同的批次版本与错误码。

## 第二阶段：并发读与重建索引

如需要并发 API 查询，可引入共享读锁与排他写锁；所有依赖数据的读取必须覆盖完整一致性范围。不得先释放锁、继续惰性读取文件，再声称仍处于同一快照。现有 read_snapshot 是协作协议下的逻辑视图，不是操作系统快照，不能防止绕过锁的编辑器、Git checkout 或人工改文件。

可以在 `.research-local/` 建立按 document_id、对象、数据集、期间、版本索引的 SQLite/其他索引。索引从正式文件重建，在新克隆或损坏后自动恢复；其版本键至少绑定所依赖的 manifest 和 metadata 修订指纹。测试必须证明删除索引不会丢失研究事实。

同一工作树有服务运行时，应协调暂停正式写入后再 git pull/checkout；跨机器的两个克隆不共享本地 flock。Git 合并后必须校验重复 ID、批次冲突、修订分叉与来源哈希，不应把 Git 合并成功视为数据准入成功。

## 第三阶段：规模提升时的替换点

当全库一次验证本身成为瓶颈，再考虑内容寻址清单树、可验证增量索引、分区读范围与批量事务。增加批量准入需要一次审核绑定多个候选、一个清晰基线和可恢复提交清单，不能用循环中关闭校验来实现。

未来可替换 repository 的存储适配，但 domain 合同、来源证据链、精确期间与维度、追加版本、PIT 规则及公共服务入口保持稳定。部署数据库或对象存储是实现选项；用户要求保留在 Git 的正式事实仍需可导出、可校验并能在新克隆恢复。不会把隐式运行缓存变成唯一事实来源。

## 暂不承诺

当前没有分布式锁、跨克隆事务、OS 级不可变快照或零成本全库校验。`write()` 的原子文件发布与以 batch manifest 为可见边界提供单批恢复能力，不等于多个批次共同提交的全局原子事务。以上边界应在增加 Web 服务、worker 和定时采集前保持明确。


## 优化后复测

在同一真实工作区选择已入库的日行情候选执行 plan 与幂等 apply：plan 0.441 秒、索引构建 1 次；apply 0.307 秒、索引构建 1 次，返回 unchanged。结果见 `optimized-admission-profile.json`。正式数据未新增或覆盖；新批写入路径由单元测试验证，本次没有为了基准制造正式批次。这不是新入库端到端性能 SLA：网络下载、PDF 提取、人工审核、写盘耗时未包含在这个幂等测量中。

后续链路复查还发现 acquisition.run 在入库完成后、acquisition.status 在回查任务时直接调用 batches，绕开了上述阶段缓存。现已分别加入新的 read_snapshot：入库后重新读取并实际校验提交结果；status 将列表原件、任务状态、正式批次和来源原件放在同一个只读阶段中，退出即失效。新增多批次回归确认每阶段单索引，并在下一次 status 前对原件做同大小修改，仍以 EVIDENCE_CHANGED 拒绝。相关 acquisition 与准入缓存测试 27 项通过。此修复不复用写入前缓存，也不跳过任务完整性复核。

最终跨克隆恢复暴露的候选验证/复核读阶段也已使用独立read_snapshot，退出后才写验证/审核回执；新请求重新核验原件。旧公司行动可选字段通过规范化比较视图兼容，原存储字节保持不变。新回归覆盖跨请求原件篡改及旧字段缺省重放。
